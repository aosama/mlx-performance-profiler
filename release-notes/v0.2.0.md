# mlx-performance-profiler 0.2.0: know whether your version is really faster, and read every node's cost as data

This release is for anyone tuning MLX code on Apple silicon who needs to know whether a change really made it faster. Hand the profiler two implementations of the same job, such as a stock MLX primitive and your own Metal kernel, or eager and compiled, and the report opens with a verdict: which is faster, by how much, and whether the difference is bigger than run-to-run noise. Every profile now also writes its measurements as JSON, so a test or a script can read what each node cost without parsing the HTML. On a Qwen3.5-0.8B decode step at context 1024: *compiled is 5.6% faster than eager, faster in 12 of 12 rounds.*

## Highlights

**Know whether your version is really faster (#12).** A kernel author's question is rarely "how long does this take" but "is mine faster than the stock one, and is the difference real". Pass two graph callbacks to `mlx_perf_compare_to_report` and the comparison page opens with one sentence. For the Qwen3.5-0.8B decode step at context 1024, eager against compiled: *"compiled is 5.6% faster than eager (175.2 µs of 3.11 ms, faster in 12 of 12 rounds). 96% interval for the per-round difference: −188.8 µs to −164.4 µs. The difference exceeds the spread."* The two variants run in 12 interleaved rounds with the order flipped every round, so a slowdown on a busy machine lands on both. This matters: measured one after the other, compiled read 4.2 ms against eager's 3.2 ms, because it ran later and absorbed a step of about 1 ms that job duration took partway through the run. Interleaved, compiled is faster in every round. A difference counts only when the candidate won at least 10 of 12 rounds, so two identical variants are called different under 4% of the time. That guarantee is asserted in the test suite over 4,000 seeded trials (#22, #23).

**Read what every node cost, from a file (#11).** Before, a caller got ten headline numbers and an HTML page; a test could not assert on what one node cost without scraping the page. Now every profile writes `<base>.json` beside its report: one record per node in execution order, with the node's GPU execution window read from its Metal command buffer, how long its stream's GPU sat idle before it, its six waiting and computing slices, its serial time and the memory it added. A value that was not measured is `null`, never zero. `mlx_perf_profile_to_measurements` writes the file alone, without the report. On Qwen3.5-0.8B-MLX-4bit the file holds 1,144 eager nodes (#21).

**Quiet when used as a library (#24).** `mlx_perf_set_console_output(0)` stops everything the library prints, so a consumer's own stdout stays machine-readable. Failures still come back as return codes and `mlx_perf_last_error()` (#26).

**The live view gives the same verdict (#25).** `mlx_perf_server` now measures eager against compiled as an interleaved pair, and its Job tab opens with the same verdict as the static page. On the server's built-in demo job it read *"compiled is 33.8% faster than eager … faster in 11 of 12 rounds"* (#26).

## Get started

**From source with CMake FetchContent:**

```cmake
include(FetchContent)
FetchContent_Declare(mlx_perf
  GIT_REPOSITORY https://github.com/aosama/mlx-performance-profiler.git
  GIT_TAG v0.2.0)
FetchContent_MakeAvailable(mlx_perf)   # with -DMLX_PREFIX=... on your command line
target_link_libraries(my_test PRIVATE mlx_perf::mlx_perf)
```

Only the library is built (no tools, tests or install rules), and only the C API's headers reach your include path.

**As an installed package:**

```sh
git clone --branch v0.2.0 https://github.com/aosama/mlx-performance-profiler.git
cd mlx-performance-profiler
cmake -S . -B build -DMLX_PREFIX=/path/to/mlx/prefix \
      -DMLX_PERF_BUILD_TOOLS=OFF -DMLX_PERF_BUILD_TESTS=OFF
cmake --build build
cmake --install build --prefix /path/to/install
```

```cmake
# In the consumer: cmake -DMLX_PREFIX=... -DCMAKE_PREFIX_PATH=/path/to/install
find_package(mlx_perf 0.2 REQUIRED)
target_link_libraries(my_test PRIVATE mlx_perf::mlx_perf)
```

`MLX_PREFIX` points at a prebuilt MLX of a tested release (0.32.4 or 0.32.5). An installed package accepts only the MLX release it was built against.

**Pinning the source archive:**

```sh
curl -LO https://github.com/aosama/mlx-performance-profiler/releases/download/v0.2.0/mlx-performance-profiler-0.2.0.tar.gz
echo "d8ad4c93a449abee130a1bdac6f759542ae9dd297694104959aa3abd27d04fe5  mlx-performance-profiler-0.2.0.tar.gz" | shasum -a 256 -c
```

**Compare two implementations** (from the README):

```c
mlx_perf_variant stock  = {"stock",  build_stock_graph,  &stock_payload};
mlx_perf_variant custom = {"custom", build_custom_graph, &custom_payload};
mlx_perf_comparison_summary summary;
mlx_perf_compare_to_report(&stock, &custom, "My projection", "build", "projection", &summary);
```

This writes `build/projection.html` (opening with the verdict), `build/projection.json`, and a report and measurement file per variant. `summary.job_wall`, `summary.gpu_span` and `summary.host_submission` each carry a `verdict` (`MLX_PERF_VERDICT_CANDIDATE_FASTER`, `_WITHIN_SPREAD` or `_SLOWER`).

Full documentation at this tag: [Comparing two implementations](https://github.com/aosama/mlx-performance-profiler/blob/v0.2.0/README.md#comparing-two-implementations), [Per-node measurements as data](https://github.com/aosama/mlx-performance-profiler/blob/v0.2.0/README.md#per-node-measurements-as-data), [Use it from another build](https://github.com/aosama/mlx-performance-profiler/blob/v0.2.0/README.md#use-it-from-another-build).

## What's new

### Comparing two implementations of one job (#12)

`mlx_perf_compare_to_report` (C) and `measure_pair` with `write_report_bundle` (C++) take two graphs that compute the same result. The profiler:

- **checks the outputs agree** in count, shape and dtype before timing anything. A mismatch fails, names both shapes and writes nothing. The largest value difference is reported but never enforced, since a custom kernel may differ from a stock primitive in the last bits;
- **runs 12 interleaved rounds** with no per-node instrumentation, flipping which variant goes first, so each variant runs first in exactly half;
- **judges three metrics on the per-round differences** (candidate minus baseline): job duration, GPU span (the whole job timed as one unit per stream) and host submission (host time inside the job's `async_eval`). Taking differences round by round cancels drift both variants share. A verdict needs the whole 96% interval for the median difference (the 3rd to the 10th smallest of the 12 differences) on one side of zero. The exact sign-test p-value (how likely a split of wins at least that lopsided would be if neither variant were faster) is in the JSON.

Then one per-node timeline per variant draws the DAG, Gantt chart and task table. It is never used for the verdict.

Files: `<base>.html` (the comparison), `<base>.json` (the comparison record, `"kind": "comparison"`), and `<base>_<variant>.html` and `.json` per variant. The result also comes back in `mlx_perf_comparison_summary`. `hello_world` and `qwen35_profile` now measure eager against compiled this way. PRs #22 and #23; [docs](https://github.com/aosama/mlx-performance-profiler/blob/v0.2.0/README.md#comparing-two-implementations).

### Per-node measurements as data (#11)

`mlx_perf_profile_to_report` now also writes `<report_file_base>.json`, and the new `mlx_perf_profile_to_measurements` writes only that file (no DOT, SVG or HTML). `hello_world` and `qwen35_profile` write `<base>_<variant>.json`. The HTML and the JSON are built from the same measurement in the same call, so they cannot disagree.

- **Each node:** primitive name, and for a custom Metal kernel its `kernel_name`; stream, integer shape, dtype and output bytes; its inputs and the previous node on its stream; issue, completion and GPU start and end times; the six slices, which sum to its wall time; `gpu_idle_before_us`; serial time and memory added.
- **The job:** every job-wall sample with the median and range, the command buffers the timeline pass observed, and the time spent inside your own graph-building callback, per pass and per call.
- **Stage-timed runs** (large graphs such as Qwen3.5) add one record per stage, and member nodes carry `null` timing rather than borrowed numbers.

Schema version 1, documented field by field in [`docs/measurement-file.md`](https://github.com/aosama/mlx-performance-profiler/blob/v0.2.0/docs/measurement-file.md). PR #21.

### Silencing the library's console output (#24)

`mlx_perf_set_console_output(int is_enabled)`, on by default, process-wide and thread-safe. Off, the library writes nothing to stdout or stderr, including Graphviz `dot` errors. PR #26; [docs](https://github.com/aosama/mlx-performance-profiler/blob/v0.2.0/README.md#quiet-output-for-library-use).

### Live view: an interleaved pair with a verdict (#25)

`mlx_perf_server` measures with `measure_pair`. The Job tab opens with the verdict, and the status line follows the paired phases, then shows the verdict sentence. The other tabs keep the per-variant views. PR #26; [docs](https://github.com/aosama/mlx-performance-profiler/blob/v0.2.0/README.md#live-view).

### Smaller additions

- Custom Metal kernels are told apart by name (`kernel_name` in the JSON), read through a checked `dynamic_cast` (#21, #23).
- The Rust example declares the new C functions, with C and Rust tests pinning the same struct sizes (#23).
- The release workflow uses the Node 24 versions of its actions (#19) and refuses a tag that is not on `main` (#23).

## Upgrading from 0.1.0

1. **Change your version pin.** Before 1.0 the package accepts the same minor version only, so `find_package(mlx_perf 0.1)` does not find 0.2.0. Use `find_package(mlx_perf 0.2 REQUIRED)`, or `GIT_TAG v0.2.0` with FetchContent.
2. **Expect one more file.** `mlx_perf_profile_to_report` now writes `<report_file_base>.json` beside the `.html`.
3. **Peak memory changed meaning.** Serial-pass peak memory is now counted above what was already allocated when the pass began, so it no longer includes memory held from before the pass.
4. **Source builds are optimised by default.** A FetchContent consumer that sets no build type now gets `-O2` for the library, and no longer sees the library's internal headers.
5. **Patched MLX:** the README now lists a fifth MLX behaviour the library relies on, `CustomKernel`'s `state()` holding the kernel's name. Without it, custom kernels simply get no `kernel_name`.

0.1.0 C calls and structs are unchanged: `mlx_perf_profile_to_report`, `mlx_perf_job_summary`, `mlx_perf_version` and `mlx_perf_last_error` keep their signatures and layout.

## Fixes

- **Caller strings no longer reach a shell.** In 0.1.0, rendering the plan with Graphviz ran `dot` through `std::system`, with the output directory and file names inside double quotes, where `$(…)` is still executed. A caller-supplied name could therefore run a command. `dot` now runs through `posix_spawnp` with an argument vector, tested with a `$(touch …)` name (#23).
- **An optional `find_package` without `MLX_PREFIX`** used to stop the consumer's configure. It now reports the package as not found (#23).
- **Source consumers** no longer receive internal headers, and an untyped build is no longer compiled at `-O0` (#23).

## Compatibility

- **MLX:** the declared tested releases are 0.32.4 and 0.32.5. This release's own test run used MLX 0.32.5; it was not re-run against 0.32.4, which continuous integration (#20) is meant to cover. Metal backend, macOS on Apple silicon. Configure warns, without failing, on an untested MLX.
- **C API:** added `mlx_perf_compare_to_report`, `mlx_perf_profile_to_measurements` and `mlx_perf_set_console_output`, plus the structs `mlx_perf_variant`, `mlx_perf_metric_comparison` and `mlx_perf_comparison_summary`. Nothing removed.
- **File formats:** the measurement file and the comparison record are both `schema_version` 1, new in this release.
- **Version promise:** under [`VERSIONING.md`](https://github.com/aosama/mlx-performance-profiler/blob/v0.2.0/VERSIONING.md), a C API that only gains functions is a minor release. The installed package matches on the same minor version before 1.0.

## How this release was verified

- **Tests:** 53 registered tests, up from 38 in 0.1.0: unit, component, integration (on the Metal GPU), acceptance and packaging. All 53 passed before the release, on MLX 0.32.5 (#26, #27).
- **Acceptance test for #12:** one 4-bit quantized 2048×2048 projection, computed by `quantized_matmul` against `dequantize` followed by `matmul`. It passed 3 of 3 consecutive runs, and the fused kernel won 12 of 12 GPU-span rounds in every run (#23).
- **Packaging:** the test suite installs the library into a scratch prefix and builds, links and runs a C consumer against it. It also builds and links that consumer through the FetchContent declaration shown above, pointed at the checkout under test. 0.1.0's tests only configured that path without building through it; the new test caught a defect on its first run (#13, #23).
- **Real model:** `qwen35_profile` on Qwen3.5-0.8B-MLX-4bit wrote the measurement files (1,144 eager and 766 compiled nodes) and the paired comparison quoted above (#21, #22, #23).
- **Live view:** checked in a browser, showing the verdict on load and after Re-run (#26).
- **Rust example:** `cargo test` 4 of 4 (#23, #26).
- **Reviews:** a code review ran before each pull request. An independent, read-only review of #11, #12 and #13 then found defects in the new comparison code before it was released, all fixed in #23: the first comparison rule called two identical variants different in 22–38% of comparisons (the interval rule above replaced it); NaN outputs read as perfect agreement; and two variant names differing only in case overwrote each other's files (now refused, with report links percent-encoded).

## Known limitations and what's next

- macOS and Metal only.
- No continuous integration yet: the suite runs on a maintainer's machine before each tag. The acceptance test's GPU assertion depends on timing (a roughly 6× margin) and should be watched once CI exists.
- For a sub-millisecond job, job duration is honestly reported as inside the spread when the machine is noisy.
- In stage-timed runs, per-node waiting is not observable, and the command buffer count is a lower bound.
- An installed archive works only with the MLX release it was built against; build from source for another tested release.
- The Rust example reads this repository's build directory, not an installed prefix.

Open roadmap:

- #20 Continuous integration: build and test against every tested MLX release
- #15 Support Linux with MLX's CUDA backend
- #14 Research: how should callers in C, C++, Swift, Python, Rust and Node use the profiler?
