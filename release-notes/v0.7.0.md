# mlx-performance-profiler 0.7.0: see whether memory or arithmetic held each kernel back, and profile on CUDA

![The Data and arithmetic section of a report: this Mac's measured reading ceiling and arithmetic ceiling, then one row per operation with its bytes moved, its arithmetic, the share of its GPU time each would need at the ceilings, and a verdict: data movement, arithmetic or neither.](https://raw.githubusercontent.com/aosama/mlx-performance-profiler/v0.7.0/release-notes/media/v0.7.0-data-and-arithmetic.png)

*Drawn by the profiler itself: the new "Data and arithmetic" section of the `hello_world` report, a three-stream toy job (an `AddMM`, then elementwise operations over 2 to 24 MiB). Its streams overlap, so concurrent kernels share the GPU and read lower shares than they would alone. One run on one Mac.*

A profile said how long each operation ran on the GPU, but not why. 0.7.0 says why: for every operation, or every stage of a stage-timed job, how much of its GPU time moving its data and doing its arithmetic would each need at this machine's measured ceilings, and which one held it back, or neither. "Neither" is often the most useful answer, because it marks a kernel the GPU was not kept busy by, where a rewrite can still win. This release also brings the profiler to Linux with MLX's CUDA backend.

## Highlights

**Data movement or arithmetic, for every operation (#59).** On Apple silicon the GPU reads unified memory directly: data moves into its caches and registers while a kernel runs, overlapped with the kernel's arithmetic, so no clock can split a kernel's time between the two. The profiler answers the question that can be answered exactly:
- **Ceilings measured on your machine,** once per process, with MLX's own kernels: how fast the GPU reads memory (a reduction over 512 MiB, far larger than any cache) and how fast it multiplies matrices (a 4096 × 4096 × 4096 multiply in `float16` and `bfloat16`, the faster one). In the run behind the picture: 266 GiB/s and 25.4 TFLOP/s.
- **Bytes and arithmetic from the captured graph:** every distinct input once at its stored size (quantized weights as packed), every output, and two operations per multiply-add for matrix multiplies and fused attention. A gathered expert multiply (`GatherQMM`, `GatherMM`) counts only the experts its indices named in the run, which is what a mixture-of-experts layer actually reads.
- **A verdict per unit:** the larger of the two shares names the limit when it fills at least half the GPU time; otherwise **neither**.

In the profiler's own live check, elementwise kernels over 8 MiB (`Exp`, `Sin`) reached 90 to 95% of the reading ceiling and were judged data movement, which is what a correct calibration shows. Runs vary: where streams overlap, kernels share the GPU and read lower, as in the picture.

**Profile on Linux with MLX's CUDA backend (#15, #58).** The profiler builds against an MLX built with its CUDA backend and measures NVIDIA GPUs through CUPTI, NVIDIA's observation interface: each timed unit's GPU window, every kernel launch's name and shape, and the host's hand-offs. The Metal implementation is unchanged behind the same interfaces.

## Get started

**From source with CMake FetchContent:**

```cmake
include(FetchContent)
FetchContent_Declare(mlx_perf
  GIT_REPOSITORY https://github.com/aosama/mlx-performance-profiler.git
  GIT_TAG v0.7.0)
FetchContent_MakeAvailable(mlx_perf)   # with -DMLX_PREFIX=... on your command line
target_link_libraries(my_test PRIVATE mlx_perf::mlx_perf)
```

**As an installed package:**

```sh
git clone --branch v0.7.0 https://github.com/aosama/mlx-performance-profiler.git
cd mlx-performance-profiler
cmake -S . -B build -DMLX_PREFIX=/path/to/mlx/prefix \
      -DMLX_PERF_BUILD_TOOLS=OFF -DMLX_PERF_BUILD_TESTS=OFF
cmake --build build
cmake --install build --prefix /path/to/install
```

```cmake
# In the consumer: cmake -DMLX_PREFIX=... -DCMAKE_PREFIX_PATH=/path/to/install
find_package(mlx_perf 0.7 REQUIRED)
target_link_libraries(my_test PRIVATE mlx_perf::mlx_perf)
```

`MLX_PREFIX` points at a prebuilt MLX of a tested release (0.32.4 or 0.32.5). An installed package accepts only the MLX release it was built against.

**Pinning the source archive:**

```sh
curl -LO https://github.com/aosama/mlx-performance-profiler/releases/download/v0.7.0/mlx-performance-profiler-0.7.0.tar.gz
curl -LO https://github.com/aosama/mlx-performance-profiler/releases/download/v0.7.0/mlx-performance-profiler-0.7.0.tar.gz.sha256
shasum -a 256 -c mlx-performance-profiler-0.7.0.tar.gz.sha256
```

**See the section in the picture.** Nothing to call: every profile now has it. Build the repository at this tag and run the toy job:

```sh
cmake -S . -B build -DMLX_PREFIX=/path/to/mlx/prefix
cmake --build build
./build/hello_world
open build/hello_world_eager.html   # the "Data and arithmetic" section, under Tasks
```

From code, read it from the measurement file: `job.machine_ceilings`, and `data_and_arithmetic` on every node and stage, whose `limited_by` is `"data_movement"`, `"arithmetic"`, `"neither"` or `null`.

Full documentation at this tag: [what held a kernel back](https://github.com/aosama/mlx-performance-profiler/blob/v0.7.0/docs/reading-the-report.md#data-movement-or-arithmetic-what-held-a-kernel-back), [the JSON fields](https://github.com/aosama/mlx-performance-profiler/blob/v0.7.0/docs/measurement-file.md#nodes), [all guides](https://github.com/aosama/mlx-performance-profiler/blob/v0.7.0/docs/README.md).

## What's new

**Data movement or arithmetic (#59, #60).**
- **Report:** a **Data and arithmetic** section after Tasks: the two ceilings, the GPU time judged and what its bytes and arithmetic need at the ceilings, then a sortable row per operation (per stage task in a stage-timed report) with bytes moved, arithmetic, each share, two bars and the verdict. A share above 100% means the kernel beat the calibration kernel, as a quantized multiply can.
- **JSON:** `job.machine_ceilings` (`memory_read_bytes_per_second`, `arithmetic_operations_per_second`, `arithmetic_dtype`), and `data_and_arithmetic` on every node and stage: `bytes_read`, `bytes_written`, `arithmetic_operations`, `gathered_experts_total`, `gathered_experts_used`, `data_movement_at_ceiling_us`, `arithmetic_at_ceiling_us`, `data_movement_share`, `arithmetic_share` and `limited_by`. Not known is `null`, never zero. The JSON Schema covers them.
- **Docs:** a section of the report guide, the measurement-file fields, an index entry and a Context7 rule.

**Linux with MLX's CUDA backend (#15, #58).**
- One CUPTI session feeds a CUDA execution probe, dispatch recorder and submission recorder; the GPU backend is detected from the MLX prefix at configure time.
- Reports and console output name what each backend measures. Wired memory and the macOS memory pressure counters have no Linux counterpart and read as unavailable.

## Upgrading from 0.6.0

1. Move version pins to 0.7: `find_package(mlx_perf 0.7 REQUIRED)` or `GIT_TAG v0.7.0`. Before 1.0 the installed package accepts only its own minor version.
2. **JSON readers:** the files are `schema_version` 2. `kernel_dispatches[].metal_function_name` and the procedure record's `kernel_launches[].metal_function_name` are renamed `kernel_function_name`, and the top-level `backend` is `"metal"` or `"cuda"`. The new fields above are additive.
3. **A profile takes under a second longer, once per process,** for the calibration, and briefly uses half a GiB of memory, released (with MLX's buffer pool cleared) before any later reading.

Nothing else changes. The C API is unchanged: every function and struct keeps its signature and size. Every timing is measured as before: the calibration runs after all of a variant's passes and shares no pass's clock.

## Compatibility

- **MLX:** declared tested releases 0.32.4 and 0.32.5. This release's full suite passed on both, on Metal, macOS on Apple silicon. The CUDA backend was verified with MLX 0.32.5 and CUDA 13 on Linux in #58; the data-and-arithmetic code compiles there but has not been run on CUDA hardware.
- **C API:** no function or struct added, removed or changed.
- **File formats:** the measurement file and both comparison records are `schema_version` 2.
- **Version promise:** under [`VERSIONING.md`](https://github.com/aosama/mlx-performance-profiler/blob/v0.7.0/VERSIONING.md), a renamed JSON field and a new platform make a minor release before 1.0.

## How this release was verified

- **Tests:** 97 CTest tests, all passing on MLX 0.32.4 and on MLX 0.32.5 from this release's branch: unit, component, integration on the Metal GPU, acceptance, packaging and documentation. 0.6.0 had 90. New ones include:
  - `node_work_estimate_test` on the GPU: a matrix multiply, a quantized multiply with packed weights, fused attention causal and not, a broadcast counted at its source, and gathered multiplies (quantized and not) narrowed to the experts their indices used;
  - `machine_ceilings_test` on the GPU: both ceilings measured, within physical bounds, once per process, leaving nothing in MLX's pool;
  - `work_limits_test`, `work_record_test`, `timed_unit_work_test` and `report_work_limits_section_test`: the verdict at its boundary (a share of exactly one half), shares above 100%, units without a GPU window, and stage-timed runs.
- **Docs:** `docs_check.py` reports no problems, and real measurement files validate against the updated schema.
- **Reviews:** a code review ran before #60 and its findings were fixed before release: the section said "unified memory" on every backend, the calibration sat inside the serial pass's function, and four tests were missing. Capturing this page's picture found one more: units without a GPU window showed a GPU time of zero rather than none.

## Known limitations and what's next

- Procedure comparisons and comparison pages do not show the section: a procedure has no captured graph to count bytes from.
- Bytes are counted as traffic to memory. A small intermediate that stays in a cache between kernels is counted all the same, so for small tensors the data share can read high. Traffic between the caches themselves needs the GPU's hardware counters (Instruments) and is not measured.
- Arithmetic is counted for matrix multiplies and fused attention only; elementwise and normalization operations show "not counted".
- Open: #14, how callers in other languages should use the profiler.
